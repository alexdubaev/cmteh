# СМ ТЕХНО на OpenCart

Витрина и заявки работают на PHP, OpenCart и MySQL. В корне репозитория находится эталон Next.js. Сравнение выполняется с его коммитом `61a10e2d6a747478fc8017475d5a06ceafbc5538`.

| Путь | Содержимое |
| --- | --- |
| `extension/cmteh/` | Расширение OpenCart, витрина Twig, каталог, редактор и заявки |
| `packaging/` | Сборка установочного ZIP, правила Apache и перенос конфигурации в закрытый каталог |
| `bin/` | Локальная приёмка, импорт, генератор тестового каталога и обработчик очереди заявок |
| `fixtures/` | Синтетические данные и формат переноса |
| `tests/` | Проверки PHP/MySQL, HTTP и Chromium |

## Редактирование витрины

В админке OpenCart откройте левое меню **СМ ТЕХНО**: **Товары**, **Категории**, **Бренды**, **Страницы**, **Главная страница**, **Статьи**, **Меню и подвал**, **Заявки**, **Настройки сайта**. **Главная** показывает разрешённые прямые ссылки. **Настройки сайта** содержат реквизиты, контакты, логотип и подвал; **Меню и подвал** — ссылки шапки, подвала и юридические ссылки. Порядок задаётся полем сортировки, архивный пункт скрывается. Тексты страниц/статей и главной редактируются обычными полями и визуальным редактором. Полная карта источников, ограничения, безопасное удаление и маршрут владельца находятся в [admin-guide.md](admin-guide.md).

Оригинальные словари расширения русифицируют используемые штатные формы и вход через events OpenCart 4.1.0.4 без изменения core, языка данных и существующих прав. Происхождение, лицензия GPL-3.0-or-later и обновление описаны в [словарях](extension/cmteh/admin/language/README.md). Не устанавливайте новый язык магазина ради этого перевода.

Штатные редакторы **Каталог → Категории, Товары, Производители** подключены к витрине. В штатном редакторе категории укажите родителя для подраздела и назначьте категорию магазину. Настройки специфичных для витрины полей, например режима цены «по запросу», доступны через модуль СМ ТЕХНО. Ранее опубликованные адреса товаров и категорий сохраняются при редактировании.

Для выбора изображений оператору требуется штатный доступ к менеджеру файлов OpenCart. Публичные изображения из каталога OpenCart и медиа, одобренные в модуле импорта, хранятся по своим правилам доступа. Стартовое оформление поставляется с модулем. При установке и первом обновлении тексты и ссылки предыдущей витрины становятся записями в базе. Миграция сохраняет опубликованные правки, черновики и архивные пункты.

## Локальная приёмка

Требуются Docker Compose v2, Python 3.10+, Node.js из окружения Next.js и Chromium Playwright. Для Chromium используйте зависимости из зафиксированного `package-lock.json` корня. Дистрибутив OpenCart 4.1.0.4 берётся из официального ZIP с SHA-256 из [open-cart.lock.json](packaging/open-cart.lock.json). Локальные версии PHP и MySQL проверяющий скрипт записывает в отчёт. Проверенная конфигурация использует PHP 8.3.36 и MySQL 8.4.13.

Установите зависимости в корне репозитория. Для приёмки подготовьте 18 PNG эталона, по одному для главной, каталога, товара, корзины, брендов и статей при ширинах 1440, 1024 и 390. Снимки получают с mock-данными из отдельного checkout `61a10e2`, запущенного по корневому README на отдельном loopback-порту. Скрипт `tests/browser/capture.mjs` подходит для съёмки эталона. Задайте `CMTEH_BROWSER_BASE`, `CMTEH_BROWSER_TOOLING` и `CMTEH_BROWSER_EVIDENCE`, после чего переименуйте префикс снимков `candidate-` в `reference-`. Товар сравнения имеет адрес `/product/jd-re568158`.

```powershell
npm ci
npx playwright install chromium
python opencart/bin/verify-local --upstream <OFFICIAL_ZIP> --runtime-dir <NEW_PRIVATE_RUNTIME> --reference-dir <REFERENCE_PNG_DIR> --port 3156
```

В командах замените значения в угловых скобках на реальные пути, при пробелах заключите путь в кавычки. Runtime должен находиться вне checkout, быть пустым или отсутствовать. Порт веба привязан к `127.0.0.1`, БД доступна только внутри Compose. Если стандартный пул Docker исчерпан, проверьте существующие сети и установите `CMTEH_DOCKER_SUBNET` в свободную приватную IPv4-подсеть до первого запуска. Дополнительные параметры описаны в [dev/README.md](dev/README.md).

Скрипт проверяет ZIP и его установку штатным установщиком на пустую MySQL, PHP lint, предпросмотр и импорт демо, отдельные интеграционные проверки каталога и заявок, HTTP и SEO, сценарии Chromium, доступ к медиа, штатные роли и редактирование публикаций, повтор миграций и восстановление DB/media на копии. Все тестовые письма остаются в локальном перехвате. На рабочем месте сценарий поиска и корзины использует реальное приложение и реальную запись в MySQL. Во втором сценарии Chromium обрывает первый успешный ответ после записи в БД и повторяет запрос с тем же ключом.

После прогона проверьте `evidence/release.json`, `evidence/http-storefront.txt` и `evidence/visual-comparison.html`. Отметьте визуальную приёмку по 18 парам. Сравните подвал, навигацию, меню, карточки, типографику и мобильную компоновку. Скрипт также проверяет отсутствие горизонтального переполнения и ошибок страницы. Готовый архив и строка SHA-256 лежат в `artifacts/`. К отчёту добавьте SHA проверенного коммита, ссылку на PR, протокол локальной нагрузки и результаты визуальной сверки. Прежний проверяющий набор Next.js относится к эталону. Для OpenCart применяйте команду выше.

Для ручной проверки оставьте стенд на порту 3156. Вход администратора `cmteh-admin`, пароль хранится в файле `admin-password` приватного runtime. Остановка сохраняет тома этого стенда.

```powershell
python opencart/dev/runtime.py --runtime-dir <PRIVATE_RUNTIME> --port 3156 compose stop
```

## Установочный ZIP

```powershell
python opencart/packaging/build.py --upstream <OFFICIAL_ZIP> --output <PRIVATE_RELEASE_DIR>
Get-FileHash -Algorithm SHA256 <PRIVATE_RELEASE_DIR>/cmteh-install.zip
```

Содержимое архива и команды штатной установки описаны в `INSTALL.md` внутри ZIP и в [packaging/README.md](packaging/README.md) в исходниках. Распакуйте релиз за пределами document root. В браузере загрузите вложенный `cmteh.ocmod.zip` в **Extensions → Installer**, примените пакет, затем установите модуль **СМ ТЕХНО**. Миграции выполняются повторно через действие «Применить миграции». Версии каталога и заявок фиксируются в таблицах расширения.

В **System → Users → User Groups** создайте две группы. Штатный вход OpenCart выдаёт сессию и `user_token`.

| Группа | Access | Modify |
| --- | --- | --- |
| Оператор каталога | `extension/cmteh/module/cmteh`, `extension/cmteh/module/cmteh_catalog` | `extension/cmteh/module/cmteh_catalog` |
| Менеджер заявок | `extension/cmteh/module/cmteh`, `extension/cmteh/module/cmteh_leads` | Пусто |

Пользователь входит со своей учётной записью и открывает раздел из прямого меню. Меню проверяет существующее `access` конечного маршрута; сервер дополнительно проверяет права и сессию. Установка/upgrade не выдают роли новые права: администратор назначает согласованные маршруты через **Система → Пользователи → Группы пользователей**. Штатные формы требуют отдельных `catalog/product`, `catalog/category`, `catalog/manufacturer`; выбор изображения — `common/filemanager`. Права на установщик, управление пользователями и действие миграции остаются у администратора. Диагностика отсутствующих маршрутов закрытого стенда приведена в [инструкции](admin-guide.md#что-установлено-по-окружениям).

Перед переносом сверяйте источник данных и карту URL. Синтетическая выборка этого прогона взята из эталона. Формат NDJSON, предпросмотр, контрольная сумма входа, повтор и явное снятие с публикации описаны в [fixtures/README.md](fixtures/README.md). Для будущей выгрузки запишите, кем одобрены товары, бренды, категории, поля, страницы, перенаправления и медиа, и как обновляются данные. Разрешённые оригиналы и миниатюры кладите в приватный каталог `media/`, а связи публикуйте через импорт. В активной витрине контакты, наличие и цены должны происходить из согласованной выгрузки.

## Подготовка REG.RU

Текущая приёмка ограничена локальным стендом на синтетике. Для будущего размещения внесите в протокол значения `HTTPS_STAGING_ORIGIN`, `HTTPS_PRODUCTION_ORIGIN`, тариф, панель, объём БД, диска, inode, лимиты CPU, памяти и времени задач. Подтвердите отдельную тестовую БД, закрытый HTTPS-стенд, право пользоваться PHP CLI и cron, PHP web/CLI одной совместимой версии, MySQL и расширения из инструкции установки. Проверьте `open_basedir`, чтение каталога вне document root, `rewrite`, `mod_headers` где применимо и исходящее SMTP. Если приватный каталог недоступен из PHP, согласуйте доступ с поддержкой или выберите совместимый виртуальный тариф.

Проверьте контрольную сумму ZIP, сделайте закрытый staging, установите OpenCart и примените `setup/seal.php` из приватного каталога по инструкции установочного пакета. Передайте PHP владельцу файлов право читать закрытые конфиги. Веб-доступ проверьте отдельными запросами к конфигурации, журналам, импорту, резервным копиям и закрытым медиа. Зафиксируйте реальные пути для rewrite, `CMTEH_SITE_URL`, `CMTEH_PRIVATE_DIR` и настройки cron. Секреты размещаются в защищённой конфигурации: `DB_USERNAME`, `DB_PASSWORD`, при необходимости `DB_SSL_KEY`, пароль администратора и поля `username` и `password` в `lead-smtp.json`.

После согласования отправителя, получателя и доступа заведите приватный `lead-smtp.json` с полями `host`, `port`, `tls` (`starttls` или `implicit`), `from`, `to`, `username`, `password`. Рабочий обработчик очереди вызывается CLI. Выберите интервал по фактическим возможностям тарифа и записывайте журнал cron за пределами document root.

```text
/absolute/php /private/release/cli/send-leads.php --config=/absolute/web/config.php --smtp --limit=5
```

Сначала согласуйте с провайдером профиль, длительность, параллелизм и время проверки нагрузки, если тариф требует разрешения. На staging установите тот же ZIP и импортируйте около 100 000 синтетических товаров с репрезентативными брендами, категориями и медиа. Снимите холодные и тёплые замеры карточки, точного SKU, широкой выдачи с фильтрами и записи заявок при пакетном импорте. Запишите p50/p95, таймауты, HTTP 5xx, CPU PHP/MySQL, длительность задач, размер БД, файлов и миниатюр, число inode, место под кеш и обновление. Сверьте идентификаторы заявок с очередью. Ориентиры для согласования составляют p95 до 1 с для карточки и точного артикула, до 2 с для широкой выдачи. Для выпуска требуются согласованные пороги, отсутствие потерь заявок и измеренный запас квот. При дефиците укажите причину, оптимизацию либо подходящий тариф с ценой на дату согласования.

| Проверка | Статус для текущего прогона |
| --- | --- |
| Точная карта опубликованного сайта и перенос утверждённых данных | NOT RUN. Нет подтверждённых URL и одобренной выгрузки |
| Размещение нового ZIP, квоты и нагрузка REG.RU | NOT RUN. Закрытый test.cmteh.ru исследован только на чтение; новый пакет туда не устанавливался. Факты по БД/доступам и ограничения указаны в admin-guide.md |
| Внешние валидаторы, DNS и HTTPS, доставляемость SMTP, переключение и замеры индексирования | NOT RUN. Нет утверждённых домена, конфигурации SMTP и окна публикации |

## Обновление, резервная копия и восстановление

1. Удерживайте доступ к предыдущему пакету, его SHA-256 и инфраструктуре. Запишите версии PHP/MySQL, снимок настроек rewrite, `open_basedir`, cron и панели. Храните задания cron и настройки панели отдельным экспортом. [Область резервного копирования REG.RU](https://help.reg.ru/support/hosting/rezervnoye-kopirovaniye-hostinga/bekapy)
2. Закройте приём заявок либо переведите его на явно назначенный источник и остановите импорт и worker очереди. Сделайте согласованный снимок базы MySQL и публичных файлов, отдельный архив приватной конфигурации и медиа. Защитите копии и сохраните контрольные суммы. Для синтетической локальной копии проверяющий скрипт использует `mysqldump --single-transaction --no-tablespaces` и архив медиа.
3. Восстановите БД в новую БД, файлы в отдельный каталог, подключите их на закрытом стенде. Проверьте даты/количества, карточки, запросы, медиа и доступ менеджера к заявкам вместе с позициями и статусом доставки. В рабочем окружении перед переходом выполните финальную синхронизацию и зафиксируйте, где сохраняются заявки переходного периода.
4. Для обновления положите файлы расширения из проверенного пакета с сохранением прав, затем примените миграции в админке. Проверьте версию, витрину, HTTP-контракты и менеджерский экран. После переключения проверьте HTTPS, robots, canonical, sitemap, маршруты, очередь и согласованную тестовую заявку, сравните 404/5xx и индексирование с исходным снимком. Публикация sitemap в Вебмастере требует отдельного разрешения.
5. При откате используйте прежний пакет и текущую БД только после проверки их совместимости на копии. Перед любым восстановлением старой базы сохраните свежий снимок с заявками. Сведите заявки, принятые после старого снимка, по публичному ID и ключу идемпотентности вместе с позициями и очередью, проверьте отсутствие конфликтов и согласуйте, где менеджер будет их обрабатывать. Переключайте на восстановленную копию после сверки. В локальном gate ранний снимок показывает, почему свежая заявка пропадает при таком откате. Свежий снимок и повторное применение файлов/миграций сохраняют её и все связанные записи.
# Отдельные расценки списков

`POST /api/quote` принимает самостоятельную потребность, не позиции корзины.
JSON содержит `request_key` (UUID), `name`, `phone` либо `email`, необязательные
`message` и `page_url`, а также `input_kind: "text"` с `list_text` либо
`input_kind: "file"` с `file: {filename, data_base64}`. Для файла поле `list_text`
не передаётся. Ответ `200 {id, replayed}` подтверждает сохранение в БД;
`409` означает другой payload с тем же ключом, `429` — временный rate limit,
`503` — сохранение не подтверждено либо исчерпана квота. Повторять надо тот же
ключ и исходные данные. Ответ не раскрывает контакты, файл или ссылку на него.

Лимиты: JSON 8 МиБ, оригинал 5 МиБ, текст 1 МиБ, общая квота сохранённого
текста/файлов 256 МиБ. Разрешены XLSX/CSV/TXT/PDF/JPG/JPEG/PNG/WebP/HEIC/HEIF;
сервер проверяет содержимое и расширение. CSV/TXT принимаются в UTF-8 либо
Windows-1251, оригинальные bytes сохраняются без перекодирования. Имя, MIME,
SHA-256 и оригинальные bytes сохраняются отдельно от старых Lead-таблиц.
Файлы находятся в приватном MEDIUMBLOB, не в публичном media-каталоге.

На сервере используется **отдельный** worker из проверенного установочного
архива `cli/send-quotes.php`. До его включения создать вне webroot, в
`CMTEH_PRIVATE_DIR` (либо `DIR_STORAGE`), файл `quote-mail.json` с правами 0600:

```json
{"from":"info@cmteh.ru","to":"info@cmteh.ru","from_name":"СМТЕХНО"}
```

```sh
php /private/cli/send-quotes.php --config=/site/config.php --hosting --limit=5
```

Запускать каждую минуту через существующий cron, только после установки,
резервного копирования и проверки целевого окружения. Конкретные пути выбирает
оператор. Параллельные запуски защищены собственной DB advisory lock; всего три
попытки, задержки 60/300 секунд, lease 300 секунд при аварийном завершении.
Оригинал сохраняется при отказе MTA. Message-ID и MIME неизменны при retry;
внешняя почта не обещает exactly-once. Успех `mail()` означает только принятие
системной почтой, не попадание во Входящие. Пользовательский email используется
лишь как Reply-To, получатель и envelope статичны. Старый `send-leads.php` не
запускать для этой функции: его настройки, очередь и поведение не менялись.

Локальная проверка не отправляет почту: `--capture=example.eml` разрешён только
для loopback-витрины и пишет приватный `quote-test-capture/`. PHP integration
`tests/quote-integration.php` принимает `CMTEH_TEST_CONFIG`, создаёт только
случайный `qt_<12hex>_` prefix, удаляет лишь свои известные таблицы и fixtures,
не обращается к MTA. Strict `bin/verify-local` дополнительно проверяет native
ACL, MIME независимым parser и CLI, извлечённый из проверяемого shipping ZIP.

Миграция additive: только `cmteh_quote`, `_attachment`, `_outbox`, `_quota`,
`_rate`. При обновлении сначала свежая приватная SQL-копия и проверка чтения.
Откат к прежнему коду не требует DB rollback и не удаляет quote-таблицы;
сначала выключить только quote cron. Старый Lead worker не видит quote jobs.
Возврат нового кода восстанавливает доступ к истории/оригиналам. Не удалять
quote-таблицы или старые Lead-данные при откате.
