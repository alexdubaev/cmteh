# Спецификация: склады и предложения СМ ТЕХНО

## Задача

Одна запчасть должна иметь предложения разных складов с собственной ценой, наличием и сроком: покупатель выбирает подходящий склад. Владелец загружает остатки/цены из Excel/CSV; срок задаёт вручную для склада с уточнением по товару. Сотрудник вручную резервирует товар. Остальные направления прежнего отчёта оставлены на будущее прямым решением владельца.

## Решение

В действующей админке появятся склады, остатки/предложения, импорт, движения и резервы. Витрина покажет предложения на странице того же товара; карточка и результаты проверки списка дадут явный выбор склада. Корзина и заявка сохраняют конкретное предложение, цену и срок на момент принятия. Отправка заявки остаётся запросом расчёта, не покупкой и не резервом.

## Решения по реализации

- Действующий PHP/OpenCart/MySQL и те же IDs/публикации; новые inventoryтаблицы и same-PDO atomic ledger. Integerunits как в текущем каталоге, физические отрицательные остатки/дробные единицы не придумывать. Явная ошибка вместо округления.
- Два уровня идентичности: внутренний nativeproduct_id для складов, публичный source_id неизменен. Предложение — стабильная пара product×warehouse со своим offer_id и publicrevision. Резерв уменьшает available, не on_hand; native.quantity становится проверенным compatibilitymirror общегоavailable только после явного cutover.
- Stockauthoritative послеявного перехода managed; legacy остаются неизменны. В managed каталоге эффективнаяavailability и offerprices вычисляются из активных публичных предложений, metadataimport не затирает складскуюправду. Закрытие склада с остатком/резервом запрещено; скрытие предложения не удаляет физическийостаток.
- A01 — минимальная фиксация фактически завершённого перемещения как парного складского движения; сотрудник явно подтверждает прибытие. Отдельный dispatch/receipt/transit workflow исключён как не запрошенный. A02 — полная отгрузка ручного резерва для завершения его жизненного цикла; частичные отгрузки исключены. Оба дополнения привязаны к складам/резервам и не опережают основные требования.
- Импорт — bounded extraction существующим XLSXreader/CSVdecoder без новой зависимости, затем строгая серверная нормализация, версионныйpreview и атомарныйapply. Browserextraction не считается доказанным rawXLSX provenance: оператор подтверждает распознанные строки. Preview привязан к пользователю/сессии и хешу нормализованных данных. Нет auto product/warehouse creation и fullreplacement по отсутствующимстрокам.
- Денежные значения — decimalstrings и integer minorunits для показа, без float persistence. Публично: warehousecode/name/city, status, price/currency, deliveryterm и revision; внутренние on_hand/reserved/заметки/журнал/privateaddresses не сериализовать. Карточки показывают «Цены по складам»/доступныеуказанныецены, neverfakefixedsingleprice. Для сортировки — минимальная указанная цена доступного предложения с unknownlast, без размножения productcount.
- Публичныеwarehouselines хранятся в отдельном versioned auxiliary storage; smtechno-request остаётся legacyключом. Никакой тихой миграции выбора в старые строки. Новый endpoint /api/lead/warehouse, acceptedwarehouse snapshot side table поlead_id/position втойжеLeadтранзакции; legacy inputshape/fingerprint/propertyorder остаются прежними.
- Проверка serveroffer/revision — только для первого insert, после committedreplaylookup. Сменаостатка может потребовать refresh; запросбольшеavailable не является обещанной отгрузкой, UI обозначает количество к уточнению, запас не уходит в минус отRFQ.
- Existing CMTEH catalog access/modify служит складским read/writeACL (тот же пользователь уже имеет права на каталог/остатки); отдельные stocknativeguards не выдают новыхgrouppermissions и не изменяютadminauth. Новые роли не создаются автоматически.
- Пустые реальные склады, цены и сроки заполняются владельцем через UI/импорт; незаполненное явно показано, неfakefixtures. Текущий телефон/почта/карта/UX сохраняются.

## Границы и швы

См. interfaces.md. Файлы отчётов scouts — доказательства exactseams, не замена контрактам. Конкретные механизмы loader/DB guards проверяются installednative integration.

## Вне рамок

R01–R42 из исходногоотчёта отложены прямой цитатой «остальное оставим на будущее»: кабинеты, коммерческие заказы/оплата/налоги/возвраты, CRM, рассылки, купоны/партнёры, расширенная аналитика и условные nativeмодули. Не делаем 1С/логистическийAPI, fractionalstock/учётсерий/сроковгодности/закупки/диспетчеризациюперевозок/частичныеотгрузки, onlinepayment или автоматическое резервирование изRFQ. Нужные warehouseправа используют существующий ACL, не внедряют будущее CRMразделение.

## Открытые места

Блокирующих бизнес-вопросов нет. Имена/адреса/цены/сроки реальных складов пока не предоставлены и остаются пустыми редактируемыми данными, не заглушками функций. Никаких реальных сообщений/внешних закупок в проверках. Цель выкладки толькоtest.cmteh.ru при пройденных существующих fullgates и проверенном восстановлении.
