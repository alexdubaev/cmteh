# Спецификация: единая админка СМ ТЕХНО

## Задача

Администратор видит параллельные каталоги, установочные товары электроники и функции, которые читают не данные его сайта. Он должен управлять своим сайтом из одного понятного интерфейса и знать, какие возможности реально работают.

## 1. Единый интерфейс и каталог

- R01/R03: русская структура: Главная; Каталог; Содержимое; Обращения; Контакты; Маркетинг; Отчёты; Настройки. Логотип/название СМ ТЕХНО и текущее имя входа вместо установочного OpenCart/John Doe. Установка не меняет пользователя/пароль/группу/настройки безопасности. Главная после входа и логотип ведут на адаптированный штатный dashboard; его доступность не должна требовать выдачи новых прав.
- R04/R05/R06: один основной список товаров, категорий и брендов с данными CMTEH. Штатная расширенная форма остаётся контекстным действием конкретной записи, а не вторым каталогом в меню. Сохраняются существующие native ID, source_id, URL, поля, статусы, категории, изображения и синхронизация. Неизвестная/изменённая unmapped запись не удаляется и не публикуется автоматически; для пользователя с только штатными правами сохраняется подходящий штатный доступ. Никакого скрытого расширения ACL.
- R08/R15: полезные атрибуты/опции/фильтры и управление администраторами/группами сохраняются там, где применимы, с ясным контекстом. Инструменты, пока не используемые витриной, обозначаются в отчёте. Настройки сайта/карта, CMS, приватные файлы заявок, очереди и полезные системные инструменты остаются доступны по прежним правам. Не выводить множество установочных метрик native-заказов вместо статистики сайта.
- R01.1: меню строится с существующими access/modify разрешениями. Пользователь без права на обращения не видит их количества/контактов/ссылок; отсутствие прав не обходится через dashboard, AJAX, экспорт или прямой маршрут. Стандартные access/modify/session/token проверки сохраняются на чтение/изменения. Раздел без доступных дочерних действий не создаёт пустую группу.

## 2. Удаление установочных записей

- R02/R07: классифицировать все штатные данные и UI-модули по фактической связи с CMTEH. Положительное доказательство seed: совпадение с зафиксированным официальным OpenCart 4.1.0.4 install SQL (точные основные поля и полный набор принадлежащих строк), отсутствие CMTEH mapping и ссылок живых данных. Не считать unmapped синонимом demo. Мapped CMTEH ассортимент, даже с историческим mock source_id, является содержимым сайта и сохраняется.
- Удаляются только подтверждённые установочные сущности с безопасно замкнутыми зависимостями. Сначала dry-run с ID/типом/причиной/хешами, закрытая свежая резервная копия и проверенная процедура восстановления. Выполнение требует точного manifest/precondition hash, отклоняет изменение/новые ссылки/неожиданную схему; транзакционно, повторный запуск безопасен. Не удалять совместно используемые изображения, настройки, пользователей, группы/права, SEO сайта, обращения/оригиналы и неизвестные записи. Не удалять обязательные служебные/правовые данные лишь за установочное происхождение: их применимость и ссылки проверяются отдельно.
- D01 (проверка после T01): полезный штатный инструмент характеристик сохраняет видимость установочных CPU/Clockspeed/test1…8 даже после удаления демотоваров. Положительный аудит обнаружил 11 точных seed attributes1..11 и группы3..6, всего30строк в четырёх таблицах; их пять связей принадлежат только уже запланированным seedproducts42/43/47. Включить их в ту же guard-очистку. Сохранить owner attributes12..15, группу7 «Основные», cmteh_attribute mappings и пять строк характеристик товаров сайта. Новое использование/изменение/mapping/group member останавливает удаление. Это выполнение R07/R08, не новая возможность.
- R02.1: локальный реальный DB-тест доказывает отказ после изменения seed/появления owner reference, сохранение owner/mapped/unknown/unrelated data и восстановление удалённых сущностей. На хостинге сохранение проверяется до/после по точным хешам, не только количествам. Откат кода не восстанавливает старую БД поверх новых обращений.
- D02 (подготовка финального пакета): общий helper запускал новые integration scripts из /workspace/tests, и относительный require выбирал рабочие классы. Перед финальным strict новые cleanup/business suites должны запускаться из частной verification-directory с соседним extension, указывающим только на установленный пакет; ReflectionClass path/hash сверяется с точными членами артефакта. Ошибка пути/хеша — FAIL, без fallback на workspace. Публичный CLI и строгость остальных проверок сохраняются.
- D03 (слепая приёмка): clean Git blob seed-cleanup.json имел LF/SHA182c356f…abb4b, а подписанный физический манифест CRLF/SHAcb85…7c08. Git должен хранить именно подписанные байты: точное правило -text только для этого нового неизменяемого data-файла, без изменения runtime pin или byte verifier. Новый commit/fresh checkout обязаны давать тот же cb85… SHA; содержимое rowsets не меняется.
- Удаление ненужного интерфейса означает убрать его из основного меню и заменить неподключённые точки входа понятным описанием применимости. Не удалять движок и системные таблицы, не ломать расширенный редактор/авторизацию/обновление. Реально ненужные seed товары/категории/бренды не должны оставаться в штатном каталоге после очистки.

## 3. Обращения, контакты и отчётность

- R09/R11/R12: «Обращения» объединяет доступ к существующим заявкам корзины/короткой формы и расценкам списков. Сохраняется исходный тип/номер/дата, позиции, контакты, оригинальные файлы и состояние отправки. Существующие карточки/скачивание приватных вложений используются повторно. Это запросы на расчёт, а не оплаченные заказы; состояние почты не становится стадией продажи.
- «Контакты обращений» показывает фактические контактные данные со ссылкой на исходное обращение, его типом и датой; не создаёт customer/password/newsletter записей, не объединяет людей по совпавшему телефону/email. Поиск/пагинация серверные, безопасные связанные параметры; пустая база честно даёт ноль и пояснение.
- «Отчёты по обращениям» и dashboard показывают реальные количества по типам, датам/периоду и состоянию уведомлений, запрошенные позиции/количества. Персональные данные и исходные URL не попадают в публичный frontend/log/report. Нет выручки/оплаты/конверсии из native orders, когда коммерческого процесса нет. Итоги согласованы с доступным реестром и выбранными фильтрами; не грузят всю базу в браузер.
- R11.1/R12.1: чтение работает с имеющимися схемами Lead/Quote и безопасно показывает недоступность отсутствующей таблицы/источника; не создает/меняет бизнес-данные при GET. Нет побочных писем, изменений idempotency/fingerprints или потери неизменяемых snapshots.

## 4. Маркетинг для сайта

- R10: сохранить пригодный штатный реестр рекламных кампаний (название/код/ссылка) и адаптировать русские названия/пояснения под CMTEH. Ссылка ведёт на реальный сайт; разрешения campaign access/modify и native token сохраняются. Фактические переходы можно показывать только после проверки прохождения native startup tracking на custom CMTEH маршрутах. Отчёт явно описывает, что считается переходом, и не выдаёт его за посетителя/продажу.
- Показать доступную статистику источников реальных обращений на основе сохранённого page_url, если она есть: это указанный в обращении URL, а не подтверждённая сквозная атрибуция. Отсутствующие/неизвестные источники видны отдельно. Не менять URL при показе, не строить небезопасные ссылки/HTML; не выдавать произвольный клиентский page_url за доверенный campaign conversion.
- Штатная массовая рассылка не получает базу обращений автоматически. Без согласия/подписки/отписки полезный раздел описывает, чего не хватает; кнопка массовой отправки на случайную native/демобазу из основного интерфейса убрана. Аналогично купоны/партнёры без связанного процесса не выглядят работающими функциями сайта. Никаких реальных тестовых кампаний или писем в этой работе.
- R10.1: кампании в локальном изолированном реальном runtime проходят create/read/update и измеримый переход; права ограниченного пользователя соблюдены. Native customers/orders/newsletter/subscribers не изменяются от обращения/чтения статистики.
- D04 (слепая приёмка): две реальные local visits дали две строки marketing_report, но список кампаний показывал0; подробный отчёт сохранял «Your Store». Счётчик списка/детали должен читать одну реальную метрику и отображать2в этом сценарии; весь используемый campaign report view адаптируется к имени СМ ТЕХНО без изменения native setting/ACL. Узкая browser-проверка должна открывать фактический подробный отчёт и сравнивать список/детали.

## 5. Полная применимость и отдельный отчёт

- R07/R08/R13/R14/R16: составить матрицу ВСЕХ верхних штатных разделов и доступных типов вложенных функций (каталог/контент/расширения/оформление/продажи/покупатели/маркетинг/система/отчёты). Для каждого: что читает/меняет, есть ли связь с CMTEH, что сохранено/адаптировано/убрано из меню и почему. Матрица должна находиться в отдельном пользовательском документе и в доступном поясняющем разделе админки, без секретов и приватных данных.
- Для отсутствующих функций конкретный список разработки: публичная регистрация/вход/восстановление/личный кабинет и связь с историей обращений; полноценный коммерческий заказ с согласованной стоимостью/адресами/оплатой/доставкой/статусами; ответственность менеджеров и рабочие стадии обращений; подписка с согласием, отпиской и исключением из рассылок; применение купонов/партнёрские начисления; достоверная атрибуция/просмотры/поиск, если не измеряются. Указать необходимые решения владельца и зависимости, а не просто «не поддерживается».
- R15: существующие администраторы и группы access/modify уже могут разделять доступ к разделам; сохранить управление ими, показать как выдать ограниченные права без автоматического назначения. Различать это и отсутствующие публичные покупательские аккаунты. Не заявлять необходимость переписать вход менеджеров.

## Решения по реализации

OpenCart 4.1.0.4 остаётся движком; адаптация через расширение/штатные события, а не редактирование core и не параллельная CMS. Существующие PDO/query/render/ACL boundaries используются; новые read-only projections не меняют схему заявок. Новые зависимости/платные сервисы не нужны. Временные локальные тестовые данные изолированы от хостинга. Все admin ссылки/вывод экранируются; user_token редактируется до журналирования/артефактов.

## Границы и швы

См. `interfaces.md`; реализация детализации в двух последовательных тасках, очистка и деплой после единого проверенного результата.

## Вне рамок

Не создавать отсутствующий checkout/оплату/публичные аккаунты/CRM-процессы/согласия или складскую интеграцию без продуктовых решений. Пользователь прямо просит перечислить необходимую разработку таких функций отдельным отчётом. Это не отказ от адаптации уже доступных данных/возможностей. Реальный коммерческий ассортимент/остатки, production cmteh.ru, DNS, StoreLand, engine, новая почтовая инфраструктура — прежний отдельный объём.

## Открытые места

Продуктовых вопросов/заглушек нет. Количество безопасно удаляемых seed-записей уточняется фактическим dependency closure; небезопасный/неопределённый кандидат сохраняется с причиной в отчёте. Текущая база может измениться — финальные preconditions берутся из свежего снимка перед очисткой.
