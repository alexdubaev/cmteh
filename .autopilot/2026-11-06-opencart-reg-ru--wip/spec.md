# Спецификация: СМ ТЕХНО на OpenCart

## Задача и результат

Покупатель открывает знакомую витрину и прежние адреса, находит деталь и отправляет заявку. Менеджер редактирует опубликованные данные и видит заявки в OpenCart. Локальный кандидат устанавливается из проверенного ZIP, работает с PHP/MySQL/cron и не обращается к Node.js, Next.js или Directus. Исходный Next.js на 61a10e2 остаётся эталоном, текущие исходники сохраняются. Конкретные технические границы — в interfaces.md.

## §0. Исходные данные и выпуск

Эталон: 61a10e2d6a747478fc8017475d5a06ceafbc5538 в mock-режиме, сравнительные маршруты и снимки 1440/1024/390. Домен cmteh.ru отвечает на HTTPS, sitemap.xml вернул 404, связь с этим репозиторием и авторитетная карта пока не подтверждены. До подтверждения не считать этот хост целью переключения. Использовать синтетические данные, сверять и сохранять утверждённую выгрузку отдельно от Git. Старый CMS — источник контрактов только для чтения.

Локально: официальный ZIP 4.1.0.4 (SHA-256 cdef537f5a0a7e1b4ddbe16f589dd2e80b10150a09bfbe93ce76ef2d5c3218c0), PHP 8.3 и MySQL 8.4 в изолированных Docker-контейнерах; зафиксировать фактические patch-версии. Сверить требования установщика, mysqli/PDO, GD, cURL, zip, mbstring, XML/DOM, Apache rewrite, файловый доступ. Контроль выпуска включает применимость advisories: закрыть публичные native account, checkout, blog, upload и API, не выдавать активные SVG и запретить активные загрузки в потоке переноса; не менять ядро. Отдельно проверить доступность версий веба и CLI и расширений, HTTPS, rewrite, cron, ограничения CPU/PHP/MySQL/диска/БД/inode, open_basedir, FastCGI, память, длительность, исходящий SMTP и восстановление на конкретном аккаунте REG.RU. Host-Lite исключён; VPS вне задачи.

## §1. Пакет и админка

Официальное ядро неизменно; собственное расширение cmteh, Twig и штатная установка расширения, startup/события OpenCart для сопоставления полного пути. Apache public rewrite направляет контролируемые запросы в OpenCart и закрывает лишние точки входа. Код и assets отделены от приватных файлов. DB/SMTP config, импорты, экспорт, резервные копии, служебные файлы и медиа находятся вне document root; веб-обвязка конфигов не содержит секретов, доступ к исходникам конфигов закрыт. Миграции идемпотентны и сохраняют данные при обновлении. Админка использует сессию, user_token и штатные права: оператор каталога и менеджер заявок раздельно; право изменения проверяется сервером для каждого действия. Приёмка: чистый checkout и пустая MySQL, проверка установки и повторного обновления, анонимный и неправильный role access, публичные 404 для приватных файлов, отсутствие запросов к внешнему CMS.

## §2. Каталог и контент

OpenCart product/category/manufacturer/attribute остаются штатными сущностями. Дополнение хранит стабильные source ID, slug, нормализованные SKU/MPN, признак индексирования, отдельные статусы цены и наличия, валюту, тип, исходные ссылки, медиа/документы, доп. коды, характеристики с единицами и подтверждённые аналоги/замены. Артикулы — строки; равный код у разных брендов различается. Публичная выборка применяет одинаковые правила публикации для списка, счётчиков, деталей, поискового API, связей, sitemap и файлов. Редактирование главной, меню, контактов, страниц, статей и SEO из админки; статус и дата публикации проверяются на сервере. HTML проходит очистку по разрешённым элементам и URI. Опубликованный объект не даёт доступа к закрытому вложению; проверять UUID и разрешение на выдачу каждого запроса, не доверять пути из URL и не выдавать прямые приватные файлы.

Импорт только явной выгрузки: предпросмотр без записи, транзакции порциями, дедупликация по source ID, отчёт с причинами, продолжение по отпечатку входа и зафиксированному курсору; конфликт идентичности или неправильный файл не трогают живые данные. Отсутствие в файле ничего не удаляет. Массовое снятие с публикации — отдельный явный режим с предпросмотром. Малый набор повторяет демо, генератор масштаба ~100 тыс. покрывает реалистичные бренды/цены/наличие/характеристики/медиа.

Поиск: 2–64 символа после нормализации, точный SKU → точный MPN → префикс → русское название/бренд; одна строка на товар, стабильная сортировка с tie-breaker по ID; по умолчанию вне поиска — фото раньше. Отдельные фильтры q/brand/category/availability/partType/sort/page; выдача 12, suggestions 6, API 10, нулевые результаты и ошибка короткого/длинного запроса. HTTP API возвращает {data,meta:{total,partial?}} по эталону. Запрос короче двух символов возвращает 200 с пустым data, больше 64 или неизвестный mode — 400. Индексы по кодам, ключам публикации и фильтров; проверить EXPLAIN и заявки при параллельном импорте. Никакого поиска по доп. кодам или автоматического вывода о взаимозаменяемости.

## §3. Витрина и заявка

Перенос JSX-композиций в Twig с теми же CSS-классами, единым набором токенов, реальными утверждёнными графическими assets и локальным Oswald/OFL. Витрина industrial v3: шапка, подвал, глобальный поиск с клавиатурой и недавними запросами, адаптивные фильтры, меню, категории, бренды, карточки, статьи, страницы, mobile bar, состояния загрузки/ошибки/пустого списка/нет фото. Не копировать демо как реальные данные; содержимое поступает из модели. Сравнение парных снимков 1440/1024/390 и сценарии референса на одинаковых синтетических данных.

В корзине сохраняются старый ключ и старые объекты, допустимо добавление опциональных полей; любые повреждённые записи нормализуются, при недоступном storage используется память страницы. Ручной список и XLSX/CSV/TXT до 5 МиБ с ограниченным разбором и номерами ошибочных строк, артикул строкой, максимум 100 строк и количество 1..100000. Неизвестное можно добавить. Цена ручного ввода только при полном однозначном совпадении артикула с учётом указанного бренда, иначе «Цена по запросу»; итоги отдельно по валютам. При отправке цена/доступность не берутся у клиента.

Публичный POST /api/lead сохраняет поля исходного контракта, JSON <=512000 байт, тело объекта, валидация типов, имени 2..100, валидного телефона 7..40 или email, артикула <=128, итогового комментария <=3000, URL <=1000, максимум 100 позиций. Обе формы требуют телефон; форма корзины запрещает пустой список, быстрый контакт допускает его, вложения запрещены. Защита rate limit/спам с нейтральными ошибками; request_key UUID, совместимое поведение отсутствующего ключа. Нормализованный отпечаток фиксируется до записи; уникальный индекс и транзакция атомарно сохраняют заявку, снимок позиций и outbox. Дубль одинакового ключа и отпечатка возвращает исходный ID/replayed, другая нагрузка — 409. Запись переживает обрыв ответа; клиент сохраняет черновик и повторяет ключ неизменённого черновика, меняет ключ после правки. После успеха вычитает отправленный снимок по идентичности строки, оставляя добавленное во время запроса. Админка показывает заявки/позиции и состояние доставки. CLI cron короткими порциями, блокировка параллельного запуска, ограниченные попытки/backoff, отказ SMTP сохраняет заявку. Тестовый SMTP перехватывается. Оплата, резервы, списания, личный кабинет и окончательные коммерческие обещания исключены.

## §4. URL, индексация и разметка

Полный публичный контракт: /, /catalog, /brands, /brand/<slug>, /category/<slug>, /product/<slug>, /articles, /articles/<slug>, /about, /contacts, /delivery, /payment, /request и опубликованные /<slug>. q/brand/category/availability/partType/sort/page, page статей, import=1&article=… сохранены. Типы маршрутов различаются полным путём, системные приоритетнее, безопасная обработка UTF-8/кодирования и канонического завершающего слеша. Переносимый URL 200, настоящий 404/410 без аналога, один прямой 301 на существующий точный аналог; штатные query-маршруты не создают публичную копию. Канонический origin задаётся конфигом, не заголовком Host. Чистая пагинация канонична сама, фильтр/поиск/сорт noindex,follow с canonical /catalog; /request noindex,nofollow. Для CMS preserve canonical/robots/title/description/OG/хлебные крошки и дату публикации.

robots.txt, sitemap.xml, sitemaps/static.xml и products-N.xml c нуля, 1000 опубликованных индексируемых товаров в части; XML содержит только канонические 200 URL. Старые /api/assets/<uuid> разрешены только для публичных файлов из карты, иначе 404. JSON-LD серверный: Product/Offer/BreadcrumbList/Organization/Article/CollectionPage/ItemList по применимым маршрутам эталона, стабильные #product/#offer/#brand. Offer только для действительной фиксированной цены с валютой, ноль только явно подтверждён, наличие только из известного статуса; скрытая/отсутствующая/запросная цена без offers; никаких фиктивных оценок. Безопасная сериализация без HTML-инъекций; сравнить видимую цену, артикул, описание и изображения. Сверить XML с полной картой и HTTP выборкой, проверить все три эталонные карточки; внешние Google/Яндекс проверки отдельно от локальных assertions.

## §5. Верификация и передача

Изолированная MySQL: интеграции импорта/сбоя/повтора, публикации и ролей, приватных медиа, RFQ/конкуренции/409/SMTP, HTTP/SEO и PHP lint. Два коротких Chromium сценария: поиск → карточка → корзина → заявка и сбой → повтор → одна заявка; дополнительно визуальная приёмка, не постоянная браузерная матрица. Один локальный documented gate PHP до push; Next.js остаётся эталоном и его проверка не заменяет PHP gate. Без GitHub Actions. Независимый обзор, синхронизация с origin/main, PR только при доказанном gate по правилам владельца.

Кандидат: точный ZIP и SHA-256, Git SHA, PR, версии, команды, отчёты импорта/URL, снимки, замеры, инструкция установки/обновления/бэкапа/восстановления. Реальный staging REG.RU требует подтверждённый отдельный адрес и доступ. До разрешённой нагрузки согласовать профиль и длительность; проверить около 100 тыс. товаров, холодный/тёплый, p95 ориентиры 1 с карточка и точный SKU / 2 с сложная выдача, CPU, MySQL, квоты, таймауты и потерю заявок при импорте. Локальная демонстрация не доказывает хостинг. Отдельно записать выводы по локальной, тестовой и рабочей среде.

Production: только подтверждённый аккаунт/точный HTTPS хост, согласованное окно, проверенный откат на копии, резервные копии БД/файлов и отдельное сохранение cron/панели. План финальной синхронизации и сохранения заявок в переходе и при откате; старую БД не накатывать поверх новых данных без сверки. После переключения HTTPS, роботы, canonical/sitemap/HTTP, очередь, согласованная тестовая заявка, базовые индексирование/404/5xx, сохранение предыдущего окружения. Записи в Вебмастер требуют отдельного разрешения.

## Вне рамок и открытые места

Оплата, аккаунты покупателей, CRM, платные модули/услуги, VPS, перенос данных или изменения другого сайта. Не определены авторитетная продовая карта URL, разрешённая выгрузка, аккаунт/тариф/квоты REG.RU, адрес staging, SMTP и окно production. Реализация и локальная приёмка продолжаются с синтетикой; соответствующие внешние проверки остаются обязательными и помечаются NOT RUN, пока ресурсов нет.
