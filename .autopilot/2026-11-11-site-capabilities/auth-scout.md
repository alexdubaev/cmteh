### Native schema and index facts

`U/system/helper/db_schema.php` is authoritative for fresh native schema:

- `:1792-1908 customer`: PK `customer_id`; `customer_group_id`, `store_id`, `language_id`; email **VARCHAR(96)**; password VARCHAR(255); `status`, `newsletter`, `safe`, `commenter`, `token`, `code`. **No verified-contact field. Email has an ordinary index at :1895, not a UNIQUE constraint.** Native register's count-before-insert does not prevent concurrent duplicate registration. A future normalized-email uniqueness guard must not blindly add UNIQUE over unknown existing customers or choose one duplicate as owner. Lowercasing differs from Lead/Quote normalization, which lowercases domain only.
- `:2482-2521 customer_token`: PK `customer_token_id`, customer_id, plaintext code TEXT, type VARCHAR(10), date_added. No code/type/customer unique constraint or expiry index in this definition.

- `:82-164 address`: PK address_id, customer_id and customer_id index; address/country/zone/default/custom fields. Reuse only if addresses are an approved account capability; do not collect delivery data just because the engine has forms.

- `:7535-7602 user` and `:7661-7685 user_group`: separate manager identity and permission JSON text. Customer groups are not manager roles.

The public account input must explicitly handle native 96-character email capacity versus Lead/Quote's 254-character contact fields; never silently truncate contacts or migrate all matching contact records.

### Claim boundaries that must precede private history

- The capability map explicitly says equal email/phone does not prove identity. No current relation can support a truthful customer history merely by enabling native login.
- Verification of today's mailbox proves present control only; it cannot prove authorship of historical guest inquiries (recycled/shared mailbox, typo, forged email, employer aliases). Do not query `WHERE lower(email)=...` or accept knowledge of public UUID/request_key as ownership. Never claim old records while replaying a guest acknowledgement under a new login.
- For new signed-in submissions, ownership must come from the authenticated server context, never client-provided customer_id/email. Preserve guest submission behavior. If accepted product policy permits ownership, use additive relation/security metadata keyed to the **native customer ID** with a unique request-owner binding and indexed customer+request ordering. This is not another password/user engine. Bind in the original submission transaction or an equally atomic authorized claim; examine replay across anonymous/account A/account B, expired/revoked sessions, same key conflicting payload, and rollback. A post-response attach-by-key without proof/locking is unsafe.
- Historical linkage requires an explicitly approved proof/manual review process and audit; absent that decision, safe default evidence is **unlinked**, not auto-owned. The report does not choose the final product policy. Do not send original files/history to an email merely supplied in a form.
- Email changes/recovery must not transfer history to a different native customer, reassign relation by contact, or make old verification valid for a new address. Download entitlement is account ownership + current authenticated session + existing original; it is distinct from manager access.
