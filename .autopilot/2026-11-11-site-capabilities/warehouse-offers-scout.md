## Minimal proposed public/view/wire contract

This is a technical contract recommendation for lead consolidation, not implemented endpoints. Backend scout owns persistence/import/ledger schema. Public allowlist should expose only approved label/city/term, never internal warehouse details.

```text
Product.id / slug / sku                        unchanged canonical identity
Product.warehouse_offers[]                     explicitly published only
  id: stable opaque offer UUID                 never reused/rebound to other product/warehouse
  product_id: canonical Product.id
  warehouse_id: stable public warehouse ID
  warehouse_label: public name
  version: positive integer/string revision    public terms revision, not a timestamp guess
  price_status: fixed | on_request | hidden
  unit_price_decimal: canonical decimal string | null
  currency: ISO-code | null                    fixed requires valid configured currency/amount
  availability_status: in_stock | on_request | out_of_stock | null
  delivery_text: manual effective term | null  product override, else warehouse term

cart selected row: existing article/title/brand/quantity/productId
                   + offerId + offerVersion
RFQ v2 selected item: article, quantity, product_id, offer_id, offer_version
server immutable item snapshot: prior product snapshot + offer_id/version,
  warehouse_id/public label, price_status/unit_price_decimal/currency,
  availability_status, effective delivery_text, captured_at
```

- Product×warehouse offer has stable ID independent of stock balance; existing canonical product IDs never change. A backend uniqueness rule for one active product×warehouse row is consistent with current owner scenario; no supplier/condition multiplication invented here.
- Version changes when public price/currency/price status/availability/manual effective term changes. If ledger-derived availability updates outside the terms revision, expose/check a distinct **public availability revision** or fold that disclosed state into revision; do not send raw balance_version and bump public version on every internal ledger event. Exact choice belongs with backend consistency implementation. Warehouse default term changes must invalidate affected inherited terms; explicit product overrides remain independent.
- Authoritative amount comes from trusted server storage, not submitted price/title/warehouse label, SKU text, localStorage, DOM attributes or totals. Public JSON exact amount is a decimal string; accepted snapshot uses DECIMAL/string without float roundtrip. Native existing product.price is DECIMAL(15,4), but new precision is owned by backend schema, not inferred from UI Number handling. Preserve confirmed-zero rules; absent amount is null/on_request. Do not mix currencies or use cross-currency min/max.
- Browser display arithmetic should use bounded scaled integer/BigInt from validated decimal strings, with explicit display rounding and overflow bounds, rather than current `Math.round(float*scale)`. Totals remain indicative RFQ calculations, not payment/locked sale amounts. No tax/FX/checkout scope added.
- On product/cards, same-currency configured public offers may show a **derived range or “от” summary labelled as such**, with offer count and explicit choice; unknown/on-request alternatives are disclosed separately. A lone minimum must not masquerade as the whole product's committed price. Mixed currencies stay separate/no single scalar minimum. Price sort should use the same declared same-currency summary if supported; otherwise label/disable unsupported range ordering rather than silently sort unrelated native price. Existing product-level legacy scalar remains legacy, not synthesized warehouse price. This is one offer-view projection, not a new pricing engine.
- `StorefrontSeo.php:112 product(...)`, :138-155 currently emits one scalar Offer. Render only actual public offers with stable `#offer-<id>` and current exact terms, or a truthful homogeneous-currency aggregate. Do not emit the native scalar as a warehouse Offer or expose private quantity. SEO/view/API need the same offer projection; product canonical URL remains one.
- Resolve selected offers by product+offer IDs in one bounded server batch (<=100 request lines) rather than the current per-SKU cart search. Concrete path naming is a lead ruling, but read operation must return per-selection matched/stale/unavailable and only public fields. GET reads do not mutate product/stock or auto-update a cart selection.

## Cart identity, legacy migration and rollback hazards

- Row identity for controls/merge is `(productId,offerId)` for selected warehouse rows, `productId` for legacy canonical unassigned rows, normalized article+brand for old freeform rows. They remain three distinct namespaces; same SKU across warehouses must never merge. `offerVersion` is content revision, not a warehouse ID. Adding the same offer at a different revision must explicitly review/refresh before combining quantities, rather than silently overwrite old terms.
- Acknowledgement subtraction additionally matches submitted selection revision, so a newly reviewed/replaced row is not removed by an in-flight older acknowledgement. Fresh quantity additions on the same submitted revision remain after subtracting only submitted quantity. Removal/quantity controls, UI focus restoration and per-line labels must include warehouse when identical SKU rows coexist.
- Continue reading **smtechno-request as an array**; do not replace it with an envelope old code cannot read. Normalize legacy records without inventing offerId/version or selecting a warehouse. New v2 fields require both product and offer selection; malformed selected rows must be visibly repairable, not converted into ordinary rows silently. Keep max bounds and storage-error fallback. Cart price refresh is display only until reviewed; no auto-import/add from search or list-check.
- Existing old cached JS strips unknown offer fields on **every read/write** and merges by productId; simple additive fields are therefore **not old-client-safe**. All four consumers (`storefront.mjs`, `request.mjs`, `parts-list.mjs`, `cart.mjs`) plus layout asset version references need one coordinated revision/cache refresh. Preserve a separate versioned original selected-row recovery copy before destructive normalization; don't restore it blindly over later user deletions/acks. An old tab modifying v1 data cannot preserve warehouse intent; detect mixed-format/version edits and ask for reselection rather than guess.
- A versioned POST also needs the mixed-tab server guard: old cached request.mjs can read selected v2 rows from the shared key, strip offer fields and submit a new legacy canonical row to `/api/lead`. Recommended new-server behavior is 409 refresh/reselect for **new canonical product rows missing selection when that product now has public warehouse offers**, while resolving committed legacy replay first and retaining freeform/unassigned legacy data visibly. This changes only first acceptance of an underspecified warehouse-enabled canonical selection; do not silently discard/auto-assign it. If lead requires all old canonical first submissions to remain accepted unchanged, v2 selected storage must be isolated from old normalizers instead; additive fields alone cannot satisfy both promises.
- Old backend LeadInput ignores offer fields, so adding `offer_id`/`contract_version` to existing JSON alone is **not rollback safe**: old code accepts the RFQ with warehouse lost. Selected-offer submissions need a versioned operation old code fails closed (e.g. a new semantic POST path such as `/api/lead/warehouse-offers`, routed to the same Lead service boundary). This is a candidate route, not a created endpoint. Existing `/api/lead` and no-offer old pending submissions keep their exact contract. A top-level discriminator old code ignores is insufficient.
- Existing Lead migrator rejects schema versions >3 (`Lead.php:38`), so directly bumping shared Lead schema blocks old binary rollback. A position-keyed additive offer-snapshot table with separate version metadata is one way to avoid that, or an explicit forward-compatible release step is required. Even nullable extra columns without version bump do **not** give working rollback: old code won't display warehouse snapshots. Preserve tables/snapshots on rollback and explicitly fail closed for warehouse RFQ until a compatible reader is restored. Do not claim rollback preserves this capability just because SQL isn't dropped.
- Preserve URL/product identity, existing guest inputs, old fingerprints/replay, private manager guards and raw Quote originals. No current catalog import should auto-create warehouses or silently interpret old scalar/native stock as warehouse ownership; Excel/CSV offer import mapping and preview/apply are backend scout scope.
