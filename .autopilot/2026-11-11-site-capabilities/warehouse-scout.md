## Transaction, idempotency and concurrency contract

1. Validate/normalize payload, ACL and actor before transaction; fingerprint all semantic fields, including versions/reason/reference. Read checks do not allocate balances or migrate.
2. Claim a unique command key, then lock stable native product identity/control row, inventory state and relevant warehouse/balance rows in a **single documented order**. Multi-product operations sort product IDs; transfer balances sort warehouse IDs. Create absent balance rows with insert-on-conflict under the same product mutex before locking them. The exact order must be shared with stock adapters and deletion/cutover guards.
3. Replay finds committed result under command lock; equal payload returns same result, conflicting payload 409. Do not reject an exact replay merely because its old expected version no longer equals current: replay resolution comes first. For a new command, compare versions under lock, validate available stock and nonnegative bounds, apply SQL guarded updates, write movement/entries and command result, update aggregate if present, commit together. A no-op count can be recorded explicitly or rejected consistently; do not invent a stock movement delta.
4. Failure at any point rolls back balances, both transfer legs, ledger, aggregate and command result together. Lost commit acknowledgement is resolved by retrying same command key. Unique constraints are required even with application locks. Bounded deadlock retries require the same command identity; no unbounded loops. Do not retry arbitrary external side effects.
5. No mail/provider call occurs in the inventory transaction. G01 has no reason to send mail. RFQ submission remains immutable and creates no inventory command/reservation; manager may attach an optional source UUID only on an explicit authorized inventory action.

Do not lock shared `cmteh_schema` rows for every movement or serialize all stock through the whole catalog. Existing `CatalogAdmin::saveFromAdmin:133` has a schema lock and obtains catalog locks in its own order. If warehouse writes also update cmteh_product projection, review lock inversion with catalog import/save. Prefer a narrow inventory aggregate/read adapter over writing catalogue metadata on every transfer. A catalog DTO can read aggregate, but search/filter/count must use the same source; no count-vs-list inconsistency.

## Compatible legacy transition: no imaginary opening warehouse

**Recommended conservative boundary for specification:** additive migration creates empty schema only. Existing product.quantity, cmteh_product.availability, source IDs and storefront output remain unchanged. Do not copy the legacy common quantity to every warehouse or infer a warehouse from product.location, store, contacts or availability text. Neither `in_stock` nor raw shared quantity proves physical placement.

Explicit cutover per product should show legacy quantity, current legacy availability and last observed version/hash, ask the manager for actual quantities/locations, and lock/recheck before accepting. A stale snapshot requires reconfirmation. Capture the previous quantity/availability in cutover audit; create ledger-backed opening allocations only for explicitly entered warehouses. Inventory stock authority changes only when manager confirms this action under the final policy.

Two compatible variants to present for final choice:

- **Complete allocation/count then activate:** manager distributes known stock fully; require allocated sum equals the confirmed legacy total for a pure allocation. If physical count differs, require an explicit reconciliation adjustment reason and record both numbers; never silently discard or duplicate the difference. Pending drafts must not count toward live physical stock. Legacy public behavior remains until activation; once activated use the chosen approved availability policy.
- **Unlocated accounting remainder, explicitly labelled:** retain known legacy total as a nonphysical unallocated bucket separate from real warehouses; a manager can allocate pieces without creating receipt stock. This needs additional invariants `allocated + unallocated = confirmed total`, explicit adjustment history and a rule whether unlocated stock is sellable/reservable. Do not present it as a real warehouse or count both total and remainder twice. More code/UI/policy than complete allocation; not a default assumption.

Before explicit cutover, existing rows may continue their unassigned legacy availability and price; newly published warehouse offers cannot be invented from that data. After cutover, required public warehouse offers must be implemented, so an admin-only overlay is an intermediate development state rather than final acceptance. Label the distinction and prevent consumers interpreting legacy common quantity as current physical totals. Do not claim warehouse/public offer integration complete while quantity sources silently disagree.

Post-cutover, choose exactly what native `product.quantity` means: recommended compatibility mirror is aggregate **available** physical quantity if future core stock consumers must see sellable units; alternatively aggregate on_hand with reservations handled outside core. These are different contracts. Never mix on_hand and available between writes. Native integer width/range must bound summed values; sum with wider checked integers and reject overflow, never wrap/cast. Transfers within eligible warehouses preserve total on_hand; reserves reduce available, not on_hand; release reverses reserved, not receipt stock. Changing warehouse eligibility must not drop balances from totals silently.

Legacy public availability may be manual `on_request` or `out_of_stock`, and current NativeCatalog preserves manual overrides in some cases. Do not universally replace those with a naive `sum>0` rule. Define how zero/unknown/disabled warehouse/manual override/backorder states map to existing statuses. Required warehouse public labels/city and availability do not require exposing private address/notes or exact numeric reserves.

### Warehouse prices and delivery terms are independent of common native price

The owner requires the same part to have different prices by warehouse. Native `product.price` is a single common legacy value and cannot represent these offers. Do not overwrite it with a sum, arbitrary first price or cheapest offer. A warehouse offer revision stores validated decimal string amount/currency and the existing `fixed/on_request/hidden` semantics, including explicit confirmed zero when supported. Use integer scaled arithmetic/decimal-safe validation, bound precision/range to approved contract (native money supports decimal(15,4)); no floating-point price arithmetic or new taxes/checkout assumptions.

Offer identity is distinct from native product identity and balance identity. Offer revision changes when public terms change (price/currency/public eligibility/manual availability/delivery); balance_version changes for physical/reservation operations. A transfer need not generate a price revision, but an independently changed **published availability** needs a public freshness/version contract. Raw internal reserve/balance versions are not public API fields by default.

Delivery term is **manual by owner decision**: store bounded default text on the warehouse and nullable explicit product/offer override, preserving blank override versus inheritance semantics. Effective public term is override when set, otherwise warehouse default. Public terms versions must change (or public snapshot dependency version must change) when inherited default changes, so old displayed terms cannot silently resolve to new text. Do not calculate destination-city SLA from warehouse name or guessed logistics; no courier/payment service assumed.

### Chosen XLSX/CSV import — reuse safely, preview then atomic apply

Existing usable parser components: `catalog/view/assets/request-import.mjs:116-166` bounds XLSX ZIP size/entries/expanded data and loads shipped `vendor/read-excel-file.min.js` v9.3.10 (license/hash documented in `vendor/README.txt`); `:181-185` decodes UTF-8 with Windows-1251 fallback. **Do not reuse `inspect()` inventory normalization at `:15-53`: that RFQ parser substitutes invalid quantity=1, clamps large counts and ignores extra columns.** Inventory must reject incorrect cells and show row/column errors, not repair financial/stock facts.

No native PHP XLSX parser/library is present. `system/QuoteInput.php:102-115` checks MIME/ZIP members only; it does not parse rows. Current PHP runtime includes ZipArchive/mbstring (`opencart/dev/Dockerfile`). A minimal supported path reuses existing browser workbook extraction/bounds with a new strict inventory column mapper, then sends normalized rows to an authoritative server preview. The server resolves every SKU/warehouse, validates every value and version, stores an immutable canonical preview/digest, and only applies **that stored preview** after confirmation; browser supplied row values receive no more trust than a manual authorized stock form. Original-file SHA can be recorded for provenance but must not be falsely described as server-verified raw XLSX interpretation. If exact raw-file-to-row attestation is required, add bounded server CSV plus fixed-template XLSX ZipArchive/XMLReader parsing (no DTD/entity/network resolution, bounded entries/expanded XML/cells/depth, no formula evaluation), ~250–450 additional LOC plus focused parser tests. Do not add a new dependency blindly; existing browser parser already supports required workbook extraction.

Proposed template headers: `sku;warehouse_code;on_hand;price_rub;delivery_term` (last optional). Use exact existing SKU normalization/identity, preserving leading zeros, with **unique native product lookup**; do not reuse public-only checkList results as unrestricted admin identity mapping. Unknown/ambiguous SKU, unknown/inactive warehouse, duplicate product×warehouse rows, missing required headers/cells, negative/noninteger quantity, invalid/overflowing decimal price, malformed CSV or unsupported workbook structure produce row errors and prohibit apply. Never auto-create products/warehouses or fuzzy-match stripped SKU. Spreadsheet SKU cells must be text; custom numeric formatting cannot safely reconstruct lost leading zeroes. UTF-8/BOM and CP1251 are supported explicitly; semicolon CSV avoids conflict with decimal comma, while delimiter/decimal normalization is deterministic and rejects ambiguous grouped numbers. Reject NUL/binary/control input, over-limit rows/bytes, encrypted/macros/external links/formulas where parsed format exposes them; do not evaluate formulas or export user fields as executable spreadsheet formulas. Reject truncation rather than apply a prefix of an oversized workbook.

`on_hand` is an **absolute physical count**, not receipt delta. Preview shows before→after on_hand, reserved/available impact, price before→after in RUB, delivery override changes and opening/activation effects; blank required price is not zero and optional blank term has documented inherit/preserve behavior. Keep existing unknown/on_request state until an explicit valid fixed price is supplied. Fixed zero requires deliberate confirmation consistent with existing confirmed-zero contract. All included rows update only their own product×warehouse keys; omitted rows are untouched and never set to zero. Managed rows preserve reservations; reject the whole apply if any count is below reserved, or stale mapping/balance/offer/warehouse dependency version changed after preview. Do not destroy/recreate reserves during an import.

`InventoryImport::preview(ParsedInventoryRows $rows, Actor $actor): Preview` returns server preview ID/digest plus errors and before/after changes. `InventoryImport::apply(string $previewId, string $digest, Actor $actor, Command $cmd): ImportResult` locks all affected products/balances/offers in sorted order, verifies every preview version, appends explicit import_count stock deltas and offer revisions, commits **all bounded included rows** with one command/result. Duplicate committed apply returns original result; differing payload/key conflicts; stale preview aborts all rows and asks for fresh preview. `CatalogImport.php:28/:39` supplies preview/hash/checkpoint ideas, but its `:80-102` batch commits and global advisory lock are not the required whole-preview atomic warehouse apply contract. Do not copy its batch behavior or call it for inventory. Initial legacy allocation via spreadsheet must obey the explicit cutover rules above: incomplete physical mapping is not an implicit zeroing or new stock receipt.

Offer publication requires real explicit warehouse/price/availability/delivery inputs, not fixture example cities/prices. Warehouse archive/public-off must stop new selections without erasing historical offer revisions or RFQ snapshots. Warehouse display label/city is public; actual access directions, contacts, notes and internal ledgers remain independently private.

Backend agreement with offer-contract scout: selected offer UUID + terms version is validated against the stable submitted product and public eligibility for a **new** RFQ; stale/missing/ineligible selection returns explicit conflict, never substitutes warehouse/price. Identical committed request replay resolves its existing ID and immutable snapshot **before** checking current offer/version. ## Native writers and guard design — preserve the catalog form

**Primary race:** user opens native product form when common quantity=10; warehouse transfer/adjustment changes its compatibility aggregate to 8; user later edits title and saves, native editProduct unconditionally writes posted 10. An after-sync hook cannot repair this atomically or distinguish real movement from stale form. Reading aggregate in a PDO before-event and changing `$args[1]['quantity']` still races against another inventory transaction unless both operations share the actual locking connection/transaction.

For warehouse-managed products only:

- The native product form shows inventory stock as read-only derived value plus link to the warehouse screen; other fields remain editable. Server-side adaptation ignores/forbids direct posted stock override under the agreed contract. Do not disable the entire native form or revoke unrelated `catalog/product` rights.
- A scoped native model wrapper can run native edit under a transaction on **the registry native DB connection**, lock the common product row, read current inventory aggregate on that same connection, replace posted quantity with the controlled value, invoke the original core implementation, and commit/rollback with `try/finally`. Warehouse PDO transactions acquire the same product mutex, so they cannot interleave the mirror update. Do not acquire the mutex on another connection while original native SQL waits on it: that deadlocks the request. Verify original core helper callbacks and after-hooks do not create nested transactions or reorder locks. `native:system/engine/loader.php:319 callback` passes route and args by reference at `:324` and resolves the possibly redirected model at `:326-351`; use this supported redirect seam with a scoped wrapper, not an ignored before-event return. Existing category guard documents that trap at `admin/controller/event/cmteh_catalog.php:55`.
- Existing `NativeCatalog::synchronize` opens its own PDO transaction after native model work; keep it after the wrapper's successful commit. **Loader redirect changes the by-reference route subsequently passed to after events, while `CmtehCatalog::synchronize` recognizes only original catalog/product.* routes. Preserve/resolve the original operation for that handler or have the wrapper explicitly perform the one postcommit projection; do not silently lose synchronization or call it twice.** It must not overwrite managed availability from legacy quantity or allow current metadata import to replace inventory-derived status when that mode is approved. Prefer effective-availability read logic scoped to managed mode; preserve stored manual metadata for reversibility.
- Direct native `catalog/product.editQuantity` and checkout addHistory stock subtraction/restock need a scoped before guard/adapter for products managed by warehouses. Since orders/checkout remain deferred, reject stock-affecting native order transitions for such products rather than invent warehouse allocation. Check both product_id and master_id, plus options. Reject before mail/history stock side effects; native mail hooks are before addHistory, so event priority and controller/model order matter. Unrelated native products/orders retain original behavior.
- Delete protection is required on native `catalog/product.deleteProduct` and CMTEH `CatalogAdmin::deleteRecord`, including selected batches: validate whole batch before deleting first item. Preserve history and product identity; archive is safe. A zero current balance does not make historical product deletion safe.
- Native copy of a managed product must not duplicate stock. Create a new unmanaged product with zero/unconfirmed stock; copy only catalog data, never balances/ledger/reserves/managed activation. Core copy inherits quantity (`native:admin/model/catalog/product.php:415-453`), so adapt the copy scope explicitly. Do not alter ordinary unrelated copies without a reason.
- Native option stock is separate (`editOptionQuantity`), and native editProduct removes/recreates options at `:327-335`; do not key physical inventory/reservations on transient option-value IDs without an approved options design. Independently identified native variant products also need an explicit master-vs-child counting rule to avoid double counting one physical unit.
- Existing CatalogWrites preserves native quantity on update, but writes availability metadata; ensure managed stock fields cannot be bypassed through CMTEH editor or catalog NDJSON. External inventory import, if chosen, needs a dedicated dry-run/identity-mapping/command adapter, not reuse of product metadata import as implicit receipts.
- Native common product price edits may still change legacy catalog metadata, but cannot edit warehouse prices or revisions; per-warehouse terms are modified only through warehouse ACL/service. Label this distinction in the native form and link to warehouse offers rather than replacing the native editor globally.

Pinned core paths can be covered by native loader hooks and installed integration tests. Arbitrary third-party direct SQL bypasses loader events and cannot be claimed safe from source-only inspection. No third-party stock extension is in the shipping source inventory; any future installed writer requires compatibility review. Do not introduce DB triggers or globally disable native SQL as an unrequested architecture change.
